# История WoRkPlace

Полный журнал решений, проверок в шлеме и причин ошибок по срезам (до 24.10.2026 был файлом CLAUDE.md). Не загружается сам: искать в нём grep по имени класса, функции, настройки или дате. Новые подробности — в раздел своего среза.

# WoRkPlace

VR-приложение для работы с ПК на Windows: мониторы как виртуальные панели вокруг пользователя, управление руками (основной способ) или контроллерами. Работает на ПК через OpenXR (Quest 3S по Quest Link), не автономно в шлеме.

## Окружение

- Godot 4.7.2.stable.steam: `C:\Program Files (x86)\Steam\steamapps\common\Godot Engine\godot.windows.opt.tools.64.exe`
- Windows 11 Pro, RTX 3060, активная среда OpenXR — Meta Quest Link.
- MSVC 14.51 (VS 2026 Community), Windows 11 SDK 10.0.26100 (есть C++/WinRT). SCons, CMake и Rust не установлены — SCons поставить через `py -3.12 -m pip install scons` перед первой сборкой модуля.
- MCP-сервер `godot`: запуск проекта и чтение отладочного вывода.

## Команды

- Проверка скриптов без шлема (не запускает VR-сессию):
  `& "<godot>" --headless --xr-mode off --path . --quit-after 5`
- После добавления скрипта с `class_name` сначала обновить кэш классов: `& "<godot>" --headless --xr-mode off --path . --import`
- Тесты чистых функций: `& "<godot>" --headless --xr-mode off --path . -s tests/run_tests.gd`
- Пробный прогон помощника VDD без изменений в системе: записать `<id> add|remove` в `<папка>\request.txt` и запустить `tools\vdd_helper.ps1 -Dir <папка> -DryRun`
- Запуск в шлеме: MCP `godot.run_project` или `& "<godot>" --path .`
- Сборка нативного модуля (из `native/`): `py -3.12 -m SCons platform=windows target=template_debug disable_exceptions=no -j8`. Результат — `bin/workplace_native.windows.template_debug.x86_64.dll`, в git не хранится. `disable_exceptions=no` обязателен (C++/WinRT).
- godot-cpp в git не хранится: `git clone --depth 1 --branch master https://github.com/godotengine/godot-cpp native/godot-cpp` (собрано на коммите `b8530af`, API 4.7 выбирается в `native/SConstruct`).
- Бэкап среза (a): git-тег `slice-a` и замороженная копия сцены — `& "<godot>" --path . res://scenes/baseline/hands_scene.tscn` (руки, лучи, кнопки, без нативного модуля). `src/baseline/hands_scene.gd` не править: это эталон для сравнения.
- Бэкап среза (e): git-тег `slice-e` и полная замороженная копия — `& "<godot>" --path . res://scenes/baseline/slice_e.tscn`. Скрипты в `src/baseline/slice_e/` — копии всех `src/*.gd` с классами под суффиксом `E` (`HandGesturesE`, `PanelLayoutE`…), поэтому правка основных классов копию не ломает. Общие с основной версией: нативный модуль, `tools/*.ps1` (менять только с обратной совместимостью), `user://settings.cfg`. Самоперезапуск после потери Link запускает основную сцену, а не копию. Не править.

- В `tests/run_tests.gd` фильтра нет: `_init` вызывает все группы `_test_*` подряд, итог — строка «N проверок, M провалов». Новая группа — функция `_test_…` и её вызов в `_init`. Остальные файлы `tests/*_probe.gd` — пробы с настоящим захватом, вводом или раскладкой (меняют систему на время пробы), запускаются по одной через `-s`.

## Устройство

- `src/main.gd` (~4700 строк) — единственная сцена и дирижёр: OpenXR, руки и контроллеры (`_pointers[0|1]` — по указателю на руку, поле `mode`: «рука», «контроллер», «покой»), панели, курсор, вся панель настроек, сохранение `user://settings.cfg` (`_load_settings` / `_save_settings`). Порядок кадра в `_process`: движение мира → панели → руки и указатели → жесты двумя руками, перенос, ручки, кнопки, ползунки, редактор меню → защищённый стол → курсор → лучи. Ручки, кнопки и редактор укорачивают луч через `pointer.hit_distance`; указатель, который держит панель или ручку, курсором не управляет.
- Остальные `src/*.gd` — чистые классы (`class_name`, без сцены) с тестами: жесты, позы, фильтр курсора, раскладки, мир, меню. Логику кладём туда, в `main.gd` — только связывание и узлы.
- Система меняется через внешние процессы: `DisplayTopology` (`src/display_topology.gd`) запускает `tools/display_topology.ps1` (CCD, окна, режимы) асинхронно; `VddControl` пишет запрос в `%ProgramData%\WoRkPlace\vdd` и запускает задачу `WoRkPlaceVddHelper` (`tools/vdd_helper.ps1`, от администратора).
- Нативный модуль (`native/src`) даёт `ScreenCapture`, `MouseInput` (ввод, запись клавиатуры, связь с агентом), `GlobalHotkey`, `SecureDesktop`; агент SYSTEM (`native/agent`) — отдельный exe из той же сборки.
- Git: после принятого среза — коммит, тег `slice-<буква>` (есть `slice-a`, `e`–`l`, `n1`), на GitHub (`origin`, `Cchebyrekk/WoRkSpace`) — только по просьбе пользователя. README (для людей, на русском) обновлять при закрытии среза.

## Журналы для отладки

После каждой проверки пользователя в шлеме читать самому, не просить вставлять лог:

- Godot: `%APPDATA%\Godot\app_userdata\WoRkPlace\logs\godot.log` — последний запуск; файлы `godot<дата>.log` — предыдущие (в имени время, когда запуск *закончился* и был заменён следующим).
- Топология экранов: `%LOCALAPPDATA%\WoRkPlace\topology.log` (каждый шаг, коды `SetDisplayConfig`, состояние экранов до и после), состояние — `detached.json` там же.
- Помощник VDD: `%ProgramData%\WoRkPlace\vdd-log\helper.log` (с версии 6; папку пишет только администратор, читают все; каждая команда `pnputil`/`nefconc` с кодом выхода и числом экранов), последний ответ — `response.txt`; время запуска — `Get-ScheduledTaskInfo WoRkPlaceVddHelper`.

## Принятые решения

- Логика — типизированный GDScript; сцены собираются в коде, `.tscn` минимальные.
- Нативный модуль — C++ (godot-cpp): MSVC уже есть, C++/WinRT для захвата, доступ к `OpenXRExtensionWrapperExtension`.
- Захват — Windows.Graphics.Capture, кадры остаются на GPU: D3D11 → общая текстура → D3D12-устройство Godot. Поэтому рендерер D3D12 (Mobile) не менять.
- Панели — OpenXR composition layers (Quad) с hole punch, не обычные меши.
- Раскладка — `QueryDisplayConfig`/`SetDisplayConfig`; ввод — `SendInput`.
- Распознавание жестов и пересчёт раскладки — чистые функции с тестами.
- Выход: кнопка «Выход» в VR (удержание 1 с), `Esc` в окне Godot и глобальная `Ctrl+Alt+Shift+F12` (`GlobalHotkey`, работает без фокуса). Аварийная клавиша ещё и возвращает исходную раскладку (см. срез f); «Выход» и `Esc` раскладку сохраняют — выбор пользователя 16.10.2026.
- Суставы руки, синтезированные из контроллера, рукой не считаются.
- Подключение экрана к рабочему столу (раньше кнопки «+ / − экран», убраны 18.10.2026; теперь им пользуется загрузка раскладки) меняется **топологией рабочего стола** (`tools/display_topology.ps1`, CCD API `QueryDisplayConfig`/`SetDisplayConfig`), без прав администратора и без перезапуска драйвера. Мониторы идентифицируются по пути устройства (`MTT1337#…`). Старый вариант через `ChangeDisplaySettingsEx` работал только для одного экрана: отсоединение второго возвращало первый.
- Проверено 13.10.2026: «+ / − экран» через CCD работают много раз подряд и Link не трогают. Включение даже одного экземпляра (`/enable-device`) Link перезапускает; среда шлёт `session_stopping` + `instance_exiting`, и после этого OpenXR в том же процессе не поднять: каждая переинициализация даёт `XR_ERROR_INSTANCE_LOST`. Поэтому приложение перезапускает само себя (`_restart_app`, переменная окружения `WORKPLACE_XR_RETRY` — номер попытки, до 60 раз с шагом 5 с). Новый процесс стартует через отложенный `powershell Start-Process`; `OS.set_restart_on_exit()` после потери сессии не срабатывал (процесс завершался, новый не появлялся).
- Ручные поправки своего луча (`RAY_PITCH_DOWN_DEG`, `RAY_YAW_RIGHT_DEG`, кнопки «Луч выше/ниже/влево/вправо») — добавка поверх автокалибровки, по умолчанию 0. Боковая задаётся для правой руки и зеркалится для левой. Прежние 35°/5° подбирались под старый луч и больше не действуют.
- Осторожно при проверках без шлема: перезапущенный процесс стартует уже **без** `--headless --xr-mode off` и поднимает настоящую VR-сессию в шлеме пользователя.
- Создание экземпляра VDD: после `nefconc --create-device-node` драйвер привязывается командой `pnputil /restart-device` на новом узле (проверено 13.10.2026 на `0008`, около 12 с; `/scan-devices` не помог). `nefconc --install-driver` — крайнее средство, он перезапускает все экземпляры. Link при создании всё равно перезапускается.
- Проверено 13.10.2026: после перезапуска Link приложение само вернулось на 14-й попытке (около двух минут, без нажатий), с отключённым `xr/openxr/startup_alert`.
- В системе восемь экземпляров VDD — это предел `$MaxScreens` в помощнике.
- Операции над экземплярами устройства (`/disable-device`, создание узла, `--install-driver`) перезапускают драйвер: все окна уезжают на первый экран, Quest Link переподключается. Поэтому число экземпляров меняется только кнопкой «Применить» в разделе драйвера на панели настроек (удержание 2 с), всё разом (срез g).
- Кнопки в VR (`VrButton`) срабатывают по удержанию, начатому на самой кнопке.
- Число экранов меняет `tools/vdd_helper.ps1` через запланированную задачу `WoRkPlaceVddHelper` с наивысшими правами (без UAC в шлеме). Установка — один раз вручную: `tools/install_vdd_helper.ps1` от администратора; после правки помощника установку повторить. Обмен — файлы в `%ProgramData%\WoRkPlace\vdd`; помощник принимает `add`, `remove` и `apply N` (срез g; «Применить» пользуется только `apply`).
- `.ps1` держать в ASCII: PowerShell 5.1 читает файл без BOM как ANSI.
- Мониторы идентифицировать по экземпляру адаптера или ID монитора (`MTT1337#…`), **не** по `\\.\DISPLAYnn` — эти имена меняются при каждом перезапуске драйвера.

## Нативный модуль (`native/src`)

- `win_backend.h/.cpp` — весь код Windows/WinRT (захват, горячая клавиша). Собирается как C++20; заголовки Godot и Windows в одном файле не смешивать.
- `workplace_classes.h/.cpp` — классы Godot: `ScreenCapture` (монитор → `Texture2DRD`) и `GlobalHotkey`.
- Путь кадра: WGC → D3D11-текстура с общим NT-дескриптором → `ID3D12Device::OpenSharedHandle` на устройстве Godot → `RenderingDevice.texture_create_from_extension` → `texture_copy` в текстуру, созданную самим Godot → `Texture2DRD`. Копия нужна: драйвер D3D12 в Godot 4.7 не умеет делать `Texture2DRD` из внешнего ресурса (`texture_create_shared` падает с `!owner_info.allocation`, картинка белая). `ScreenCapture.update()` вызывать каждый кадр. Синхронизации между устройствами нет (возможен разрыв кадра) — принято для первого варианта.
- Дымовой тест захвата без VR (окно на 3 с): `& "<godot>" --xr-mode off --path . -s tests/capture_probe.gd`; с `WORKPLACE_PROBE_SHOT=<файл.png>` сохраняет снимок окна. На рабочем столе проходит: ~58 кадров/с, цвета верные.
- `--import` падает с нарушением доступа, пока у пользователя открыт редактор Godot: тот держит временную копию `bin/~workplace_native…dll`, и второй экземпляр в режиме редактора не может её перезаписать. На обычный запуск проекта и на тесты не влияет.
- Не класть текстуру захвата на 3D-материал: в VR это удаляет устройство D3D12 (`0x887A0005`) и роняет движок. Через composition layer — нормально.
- Срез (c): `MouseInput` (статические `move_to`, `set_button`, `scroll` через `SendInput`, координаты — пиксели виртуального рабочего стола). `CursorFilter` (`src/cursor_filter.gd`, чистый класс) ставит нажатие туда, где луч был за `lookback_sec` до щипка, и держит курсор на месте до выхода за `drag_threshold`. Курсором владеет один указатель; нажатие считается, только если началось на панели.
- Стабильность кликов руками (по логам 14.10.2026: при удержании щипка луч дрожал на 40–90 px). Ниже `PINCH_FREEZE_DISTANCE` (3 см) и пока щипок удерживается, вклад поворота кисти заморожен (`Pointer.rotation_offset`), луч идёт только за положением руки. Сглаживание адаптивное по угловой скорости (`PointerMath.adaptive_smoothing`). Перетаскивание требует и задержки, и расстояния. Двойной клик: повторное нажатие в течение 1 с и 80 px фильтр помечает `double_click`, а `main.gd` отправляет «нажал-отпустил-нажал» подряд — иначе руками не уложиться в полсекунды Windows. С контроллером этих проблем нет.
- Луч рук: по умолчанию поза прицеливания среды (`XR_EXT_hand_interaction`, включено в `project.godot`; Link её поддерживает) — пользователю она понравилась больше. «Свой» луч по суставам оставлен на выбор и подогнан под неё по измерениям `AimStudy` (14.10.2026): доля поворота кисти 0,42, начало луча (2; 11; 6) см в системе запястья, постоянная поправка курса/возвышения медленно калибруется по лучу Meta. Баланс, ручные поправки и выбор луча хранятся в `user://settings.cfg` (секция `[ray]`, `version=2`). Кнопки в VR: «Луч: Meta/свой», «Кисть −/+», «Как у Meta».
- Срез (d): `PanelLayout.arrange` (чистая функция, тесты) раскладывает мониторы по сфере вокруг глаз: 1920 px = `PANEL_WIDTH_DEG`, ряд шире `PANEL_MAX_ARC_DEG` (300°) пропорционально ужимается; по горизонтали центрируется вся группа мониторов (не основной — пользователь ждёт средний экран перед собой), по вертикали ряд основного на уровне глаз. `ScreenPanel` (`src/screen_panel.gd`) = захват + слой; панель с меняющейся картинкой рисуется каждый кадр (`UPDATE_ALWAYS`) и ещё `ACTIVE_HOLD_SEC` после, потом `UPDATE_DISABLED`; только при видимой сессии. `UPDATE_ONCE` на каждый новый кадр давал мигание активных панелей. Список мониторов сверяется раз в секунду, при изменении (увиденном дважды подряд) панели перестраиваются целиком. Проверено коротким запуском: 8 панелей 1920×1080, 67–73 FPS при 72 Гц, ошибок нет.
- Сцена выравнивается по взгляду пользователя через 0,5 с после `session_focussed` и по кнопке «Центр» (`_recenter`); панели позиционируются глобально (`_place_panels`), хотя слой обязан быть дочерним узлом `XROrigin3D`.
- Панель: `SubViewport` с `TextureRect` → `OpenXRCompositionLayerQuad` (дочерний узел `XROrigin3D`, `sort_order` −2 и дальше по удалённости — срез j, hole punch, у главного вьюпорта `transparent_bg`; `-1` занят панелью защищённого стола, срез h).
- Срез (e): `HandGestures` (`src/hand_gestures.gd`, чистый класс, тесты) по одному на руку. Кончик большого к кончику указательного — ЛКМ, к кончику среднего — ПКМ, **к боку указательного** (расстояние до отрезка «костяшка — средний сустав», `side_press`/`side_release`) — СКМ. Трёхпальцевый щипок пользователь не смог выполнять надёжно (16.10.2026), его заменили касанием бока по выбору пользователя. Первое касание открывает окно `confirm_delay`; если за окно было несколько касаний, побеждает самое глубокое относительно своего порога; касание короче окна — щелчок. Пока не решено, `pending` замораживает курсор, а нажатие уходит на `CURSOR_LOOKBACK_SEC + confirm_delay` назад.
- Прокрутка — **диск** (первый вариант «рука вверх-вниз» работал плохо): указательный и средний прямые и смотрят вверх (`disc_up`, косинус к вертикали), большой отведён (`disc_thumb_spread` от костяшки указательного), безымянный согнут (`disc_ring_curl`, 0 — не требовать). Через `disc_dwell` появляется кольцо (`ScrollDisc`, `src/scroll_disc.gd`, чистая геометрия) в вертикальной плоскости лицом к пользователю, кончики пальцев — на его верхней точке; против часовой — колесо вверх, по часовой — вниз, `disc_turn_units` за оборот. Колесо идёт в окно под курсором от любой руки с диском (луч при поднятых пальцах смотрит мимо панели). При входе в позу курсор возвращается на `DISC_RECALL_SEC` назад (`CursorFilter.recall`). Касание пальцев во время диска блокирует щелчки до разведения.
- Поза диска уточнена пользователем (16.10.2026): пальцы «вверх» — **относительно кисти**, то есть вытянуты по её линии (`disc_align`, косинус между пальцем и направлением запястье→костяшка), и сомкнуты (`disc_together`); положение кисти в мире неважно.
- Нажатие руками ставится в момент, когда решающий палец **начал** сходиться с большим (`approach`, 4,5 см; `HandGestures.Output.anchor_time` → `CursorFilter.update(anchor_time)`), а не на фиксированное время назад: средний палец сводится медленнее, и правая кнопка промахивалась.
- Рука в покое (`HandEngagement`, `src/hand_engagement.gd`, тесты): ладонь ниже глаз больше `drop` (0,5 м) или луч ниже горизонта круче `ray_down_deg` (40°) — рука скрыта, луча нет, жесты сброшены, курсором не управляет. В покой — через 0,2 с, обратно — через 0,3 с. Пороги — на панели настроек (секция `[engagement]`); в строке `[track]` каждой руки — «ниже глаз … см, луч …°» для подбора.
- Прокрутка по умолчанию — «направление» (`ScrollStick`, `src/scroll_stick.gd`): в позе диска сдвиг кончиков пальцев от точки старта вверх/вниз/вправо/влево прокручивает в ту сторону (вертикальное и горизонтальное колесо), чем дальше — тем быстрее; работает только доминирующая ось; инверсия каждой оси и выбор «направление/диск» — в настройках (`scroll_mode`, `invert_vertical`, `invert_horizontal`).

- Отклонено пользователем: долгий щипок как ПКМ (путается с выделением). **Отложено** до конца всех срезов: переключение виртуальных рабочих столов — пользователь хочет реализовать позже в другом виде.
- Панель «Настройки» стоит позади пользователя (за дугой экранов, которая не шире 300°). Контроллер: триггер — ЛКМ, grip — ПКМ, стик — колесо. Перечисление названо `Click`, не `Button`: `Button` конфликтует со встроенным классом Godot. Все пороги — на панели «Настройки» в VR, хранятся в `user://settings.cfg`, секции `[gestures]` и `[cursor]`.
- Срезы (a)–(d) приняты пользователем к 15.10.2026. Прежний вопрос производительности (в начале сессии 10–17 с на ~36 к/с) 19.10.2026 не воспроизвёлся ни с 3, ни с 5 экранами. Осталась короткая заминка — сборка шейдеров при первом появлении материала в поле зрения (у драйвера D3D12 в Godot 4.7 нет кэша конвейеров на диске, `user://vulkan` пуст, сборка — при каждом запуске; до `session_visible` среда не просит рисовать, заранее не собрать). Было два кадра ~115 мс (первый видимый и после выравнивания через 0,5 с). Теперь всё в первом кадре: сцена выравнивается на первом кадре с отслеживаемой головой (`_update_first_recenter`, не дольше `RECENTER_MAX_WAIT_SEC`), а `_warm_up_shaders` ставит на `WARM_UP_FRAMES` кадров перед камерой копии каждого вида меша/материала и `Label3D` в масштабе меньше пикселя. Итог: один кадр ~145 мс и ~0,15 с хвоста, дальше ровные 72. Замер первых 30 с — строки `[startup]` в журнале (кадры, долгие кадры по частям `_process`, отрисовка, собранные шейдеры `RENDERING_INFO_PIPELINE_COMPILATIONS_*`); `Performance.TIME_PROCESS` для этого не годится — обновляется раз в секунду.

## Виртуальные дисплеи (VDD) на этой машине

- MTT Virtual Display Driver (`Root\MttVDD`, `oem94.inf`), конфиг `C:\VirtualDisplayDriver\vdd_settings.xml`, канал `\\.\pipe\MTTVirtualDisplayPipe`.
- С 13.10.2026 экземпляров восемь (`0006`–`0008` созданы из приложения); сколько их, меняет «Применить» на вкладке «Драйвер».
- Намеренно установлено **пять экземпляров** `ROOT\DISPLAY\0001…0005` при `count=1`: по наблюдению пользователя, пять мониторов на одном экземпляре лагали, пять экземпляров по одному — нет (причина не исследована).
- `count` читает каждый экземпляр, это множитель. **`count` не менять**, канал драйвера для числа экранов не использовать.
- Число экранов меняется на уровне экземпляров устройства (нужны права администратора):
  - отключить / включить: `pnputil /disable-device "ROOT\DISPLAY\000N"` / `/enable-device`
  - создать: `nefconc.exe --create-device-node --hardware-id Root\MttVDD --class-name Display --class-guid 4D36E968-E325-11CE-BFC1-08002BE10318` (nefconc в `C:\ProgramData\scoop\shims`); если драйвер не привязался — `nefconc --install-driver --inf-path <mttvdd.inf из DriverStore>` (код 3010 — норма)
  - удалить: `pnputil /remove-device "ROOT\DISPLAY\000N"`
  - проверка: мониторы `DISPLAY\MTT1337\*` со статусом OK (`Get-PnpDevice -Class Monitor -PresentOnly`)
- Пользователь видит ПК только через эти виртуальные экраны, поэтому:
  - UAC запрашивать один раз и заранее, всё делать в одном повышенном процессе;
  - никогда не доводить число экранов до нуля; менять по одному экземпляру и проверять после каждого шага;
  - `ROOT\DISPLAY\0000` (Meta Virtual Monitor) не трогать.
- Список разрешений в XML общий для всех экземпляров.

## Как вести работу

- Вертикальные срезы: (a) VR-сцена с руками и контроллерами; (b) один экран; (c) курсор и клики; (d) все мониторы в раскладке; (e) жесты; (f) перемещение панелей ↔ раскладка Windows; (g) VDD; (h) агент SYSTEM: окна администратора и защищённый стол; (i) основа мира; (j) шары, места, меню; (k) стена; (l) столб; (m) сеть мест; (n1) группы экранов — приняты (n1 — 23.10.2026, тег `slice-n1`, в том же коммите и (m)); (n2) редактор мира — сделан, ждёт проверки.
- После каждого среза сказать пользователю, что проверить в шлеме, и ждать ответа; коммит после подтверждения рабочего среза.
- Запуск проекта переключает картинку в шлеме с рабочего стола на VR-сцену — предупреждать перед запуском.
- Не делать на этом этапе: виртуальная клавиатура, захват окон, passthrough, автономная сборка, звук.
