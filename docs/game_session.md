# q3 — запуск и режим игр, 06.11.2026

Четвёртый WorkMode.PC_GAMES=3 отображается в общей настройке «Режим работы».
Сторож link_server_watch.ps1 запускает game_session.ps1: скрытый game_host,
SteamVR, USB reverse для 47902/47903/47920. Завершение SteamVR или хоста
возвращает сохранённый предыдущий режим; смена режима/stop завершает игровую
сессию. Быстрый выход шлема при mode=3 восстанавливает before_games.txt
и завершает хост, очистку делает session helper.

При обычном старте SteamVR наш драйвер запускает сторож с -Mode 3 (путь к
скрипту определяется относительно DLL в дереве репозитория). Сторож использует
свой существующий mutex. При обновлении старый работающий сторож нужно один
раз заменить: он держит прежний код в памяти и не знает режим 3.

game_host.cmd теперь запускает сторож в режиме 3, а не отдельный непроверяемый
хост. Наличие SteamVR ищется по openvrpaths.vrpath. Глобальный OpenXR runtime
не меняется.

player.gd читает сохранённый headset/link_mode из settings.cfg. Auto начинает
с USB localhost и использует Wi-Fi при неудаче; Wi-Fi-only исключает localhost,
cable-only исключает UDP discovery. При обрыве начинается повторное подключение.
Подключение USB посреди действующего Wi-Fi-потока не переносит поток незаметно:
новый канал выбирается при новом соединении. Порты для новых USB-устройств
повторно настраиваются каждые 5 секунд. adb имеет тайм-аут 3 секунды на команду;
опрос USB не предшествует запуску хоста (зависший adb блокировал начало сессии).

Проверки: parse_probe для изменённых скриптов, PowerShell parser, 796 проверок
чистых классов без провалов. Windows-драйвер и APK собраны, APK установлен.
После замены старого сторожа подтверждён режим 3, reverse-порты и подключение
шлема к 127.0.0.1. Завершение vrserver вернуло mode=1 и подняло link_server.
Запуск SteamVR из mode=1 записывает mode=3, новый сторож запускает игровой хост.
После тайм-аута adb подтверждён живой хост и поступление tracking/video.

Промежуточная проверка: выбор режима из панели, быстрый выход,
повторный вход, кабель и Wi-Fi-only проверялись по ходу среза; результаты
конкретных запусков и ограничения описаны ниже.

После сообщения «бесконечное ожидание картинки» воспроизведён новый запуск:
SteamVR выбрал HMD oculus.3487C10H3W02M1, драйвер workplace не активировался,
хост оставался доступен без видеопотока. Для workplace задан документированный
loadPriority=100 (встроенные драйверы имеют 0). После перезапуска подтверждены
активация workplace и первая картинка в Quest, 670–686 новых кадров за 10 с
по Wi-Fi. Хост теперь возвращает рабочий мир, если драйвер не появился за 45 с.
game_session.log дополнен шагами запуска и завершения. Профиль приоритета
действует при запуске SteamVR с установленным дополнением WoRkPlace.

Следующие исправления по проверке пользователя: before_games.txt сохраняет
предыдущий режим 0–2, выход и завершение сессии восстанавливают его вместо
безусловного 1. Событие VREvent_SceneApplicationChanged отслеживает активное
VR-приложение; процессы compositor и SteamVR Home исключены. После завершения
последнего приложения и 3 с ожидания выполняется возврат. Запуск теста дал
scene_pid=8576; закрытие теста дало 0, затем возврат в сохранённый mode=1.
Иные предыдущие режимы и запуск сторонних игр требуют пользовательской проверки.
Это относится к приложениям через SteamVR, не к нативным приложениям Meta.

Пользователь установил, что при зоне обзора 0 искажений нет. По умолчанию теперь
0; настройка «Зона обзора» общая для игр и «ПК рисует», передаётся при подключении.
Сохранённый ключ game_fov_percent не переименован ради совместимости конфигураций.
Повторная проверка после сообщения «автоматическое переключение не сработало»:
запущено только tests/steamvr_room с XR_RUNTIME_JSON=SteamVR, без ручного старта
хоста/SteamVR/режима. Журнал подтвердил runtime SteamVR и переход mode 1 → 3.
Системный ActiveRuntime на машине по-прежнему Meta: приложение, выбравшее Meta,
не загружает наш SteamVR-драйвер, поэтому таким способом не обнаруживается.
Пользователю задан вопрос о конкретном приложении и способе запуска; глобальный
runtime не менялся без выяснения сценария.

Конкретный сценарий пользователя: Battington Manor (Steam app 4198460).
Manifest_NonUFSFiles_Win64.txt содержит openxr_loader.dll; журнал Unreal пишет
Initialized OpenXR on Oculus runtime 1.208.0, затем Failed to get an OpenXR
system. Таким образом, причина обхода автоматического переключения подтверждена.
tools/set_openxr_runtime.ps1 выбирает SteamVR в HKLM ActiveRuntime, сохраняя
прежнее значение в LOCALAPPDATA/WoRkPlace/openxr_runtime_before.json; -Restore
возвращает его. Требуется администратор/UAC. Это системный выбор для OpenXR,
не правка файлов игры. Успех не считать подтверждённым до чтения ActiveRuntime
и нового журнала Battington Manor с runtime SteamVR.
UAC подтверждён, ActiveRuntime прочитан как steamxr_win64.json. Игра запущена
через steam.exe -applaunch 4198460 без ручного выбора режима. Новый журнал игры
подтверждает Initialized OpenXR on SteamVR/OpenXR runtime version 2.18.4,
сторож — переход mode 1 → 3. Ошибка создания visibility mask отмечена в игре
как отказ от маски (не равна отсутствию OpenXR-системы). Прежний Meta сохранён.
